## Главная идея

TypeScript — **структурная** (structural) система типов: совместимость определяется **формой** (набором полей и их типов), а не именем типа или местом объявления.

Java, C# — **номинальные** (nominal): класс `A` и класс `B` с одинаковыми полями — **разные** типы, пока явно не унаследуют/не реализуют общий контракт.

В TS достаточно, чтобы у значения были нужные свойства — «если ходит как утка…».

```typescript
interface Vector2D {
  x: number
  y: number
}

interface NamedVector {
  name: string
  x: number
  y: number
}

function printLength(v: Vector2D) {
  console.log(Math.hypot(v.x, v.y))
}

const named: NamedVector = { name: 'origin', x: 3, y: 4 }
printLength(named) // OK — есть x и y
```

---

## Почему это важно

1. **Гибкость** — не нужны общие базовые классы/интерфейсы ради совместимости.
2. **Ловушки** — лишние поля в объекте обычно OK при присваивании переменной; **excess property check** срабатывает при литерале (Item позже).
3. **API / DTO** — ответ бэкенда и локальный тип могут не совпадать по имени, но совпадать по структуре.

---

## Связь с работой (dealing-console)

Типичный кейс: Pinia store ожидает объект с полями `{ id, label, status }`, а из WebSocket приходит payload с теми же полями, но другим именем типа в контракте. Structural typing позволяет передать данные, если форма совпадает — без наследования.

Обратная сторона: легко «протащить» объект с лишними полями, если не включён strict excess check на литералах.

## Номинальные паттерны в TS (на будущее)

Чистого nominal typing в TS нет. Позже (Phase 4) — **branded types** (`type UserId = string & { __brand: 'UserId' }`) для различения строк с одинаковой структурой.

---

## Типичные ошибки

| Ошибка | Правильнее |
|--------|------------|
| Думать, что `interface A` и `interface B` несовместимы, если поля одинаковые | Смотреть на **структуру**, не на имя |
| Ожидать ошибку при передаче объекта с **доп.** полями в переменную | Часто OK; литерал — строже |
| Путать с `class` в runtime | `class` — и тип, и значение; structural — про проверку типов |
